# Local database snapshots

`rsrs snapshot create --note "before maintenance"` creates a consistent SQLite copy of the current library, including committed WAL data. It requires the current account key, writes private files (0600 under a 0700 directory on Unix), removes access grants from the copy and publishes a manifest only after verification. The live database and its grants are unchanged. `rsrs snapshot list` verifies each published manifest, hash, schema and SQLite integrity. It reports healthy entries and per-entry problems separately; one damaged file does not block restoring a different healthy snapshot.

The snapshot is a local database copy. Existing local metadata/index columns can contain plaintext; this is not whole-file encryption. Protect snapshots like the original library. The manifest contains no account key or session credential and is not an authorization document. It records file integrity, account/library fingerprints, schema and pinned SDK/model metadata. An encrypted challenge in the database independently verifies the account key, including for an empty library.

`rsrs snapshot restore <full-id> --confirm` is a host CLI operation. It coordinates the owned runtime shutdown, takes the library ownership lock, validates the selected snapshot and key, and creates a durable pre-restore snapshot. A busy checkpoint or remaining SQLite sidecar refuses replacement. The implementation never deletes a live WAL/SHM file. A verified private temporary database is replaced atomically, then the runtime reopens the restored library. Before replacing live data, the operation also durably publishes a private local rollback image and recovery journal. This internal image retains the original grants/outbox and is never included in the portable inventory. A startup or post-replacement failure rolls back from this exact local image, rather than from a portable snapshot that has had grants removed. After runtime verification, the internal image/journal are cleaned up; a cleanup warning means restoration was verified but local cleanup remains.

Live database symbolic links are rejected for create, restore and rollback; their targets are never silently replaced. Restoring is limited to the same account, library location and initialized schema. An older/different schema requires an explicit migration path; it is not silently treated as compatible. Access grants are not revived. A controlled process interruption immediately after replacement is tested, including recovery of original grants/data. Power-loss, full-disk and Windows file-sharing scenarios still require their respective platform tests. Unix publishes with file and directory fsync; Windows uses the same-directory native write-through move path. Neither passing unit tests nor these primitives constitute hardware power-failure testing.

Restoration does not roll back the server. Sync is quarantined in the restored database before replacement; automatic and explicit synchronization refuse before contacting the remote. Inspect the local/remote differences using read-only diagnostics. After deciding how to reconcile them, read `rsrs memory-revision --json` and explicitly run `rsrs snapshot resume-sync --reviewed-revision <token>`. If local memories changed since that revision, resumption is refused. Remote conflict writes and sync reset also respect quarantine.

A purge of live data does not erase older snapshot copies. No snapshot deletion command or automatic snapshot retention policy is introduced here. `memory_restore` in MCP still restores one tombstoned memory; it is unrelated to database snapshot restore and does not expose this host lifecycle operation.

An interrupted prepared operation blocks normal library opening until the host runs `rsrs snapshot recover --confirm`. The journal binds a private rollback image digest and account fingerprint; recovery checks library ownership and never deletes live WAL/SHM. A verified operation with only cleanup remaining is finalized rather than rolled back. Portable snapshots never revive grants; failed-operation rollback restores the grants that belonged to the original local state.

The maintenance gate remains closed through `prepared`, `installed` and commit persistence. Normal commands and all normal store-opening paths reject while it is closed. The owned runtime has a separate bootstrap path: it opens and checks SQLite and confirms the restored transaction ID, but this does not grant business access. The host verifies that store-ready proof, durably records the commit, then releases the gate while still holding the lifecycle serialization lock. A failed verified write aborts and rolls back before business access is enabled. After durable commit/gate release, recovery only finalizes metadata and never restores the old image over accepted new writes. Cleanup failure after this point can warn; commit persistence failure cannot.
